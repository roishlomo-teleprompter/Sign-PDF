# SignWay Apps Script single-owner pilot

This is an isolated prototype, not the production SignWay backend. Existing Supabase data and links remain unchanged. No live Google deployment or real-device signing has been verified.

## Setup

1. In the owner's account create a private blank Google Sheet named `SignWay Pilot`.
2. Open Extensions > Apps Script. Copy `Code.gs`, create HTML files `Admin` and `Signer`, and replace the project's `appsscript.json` (enable manifest visibility in Project Settings).
3. Run `setup_` from the editor and authorize the Drive/Sheets permissions. Reload the Sheet.
4. Deploy > New deployment > Web app. Execute as the deploying owner. Access: **Anyone**, including users not logged in (subject to organization policies). Use `/exec`, never `/dev`.
5. Open the Sheet's SignWay menu > upload. Select a PDF up to 5MB. Copy its seven-day link. No email is automatically sent.
6. Open the link in a private browser, draw a signature, navigate to the page, click its location and submit.
7. Verify the private Drive `Signed` folder and the `Requests` sheet have the signed file and final status. Retry the same submission to verify it does not create duplicates. Test expired and cancelled requests too.

## Storage and authorization

Originals and signed PDFs stay in the owner's private Drive folders. Requests/status live in the private Sheet. Contacts, Groups and Events tabs are reserved schemas only: their management UI and migration are NOT implemented in this pilot.

The public web app runs as its deployer; it does not magically switch to the visitor's Drive. This pilot must be installed separately for another owner. A central multi-user app requires separately engineered OAuth/token storage or another authorization architecture.

Owner uploads require a short-lived random bearer capability generated by the private spreadsheet sidebar; the setup/admin UI helpers end in `_` and cannot be invoked using `google.script.run`. Public recipient calls accept a high-entropy capability, store only its hash, check status and expiry, and access only its associated file. No public Drive sharing is created. Tokens are in the URL fragment, not query parameters. Anyone holding the signing link can sign; this is capability access, not proof of a person's identity.

Submission uses a script lock and a digest for replay detection. A retry after a lost response reuses the same PDF bytes. The server validates size and PDF header; it does not independently render or cryptographically validate the submitted PDF. This is a drawn electronic signature pilot, not a certificate-based digital signature or legal identity verification service.

## Limits before production

- 5MB per original and signed file; base64 transport increases payload size. Real 5MB roundtrip testing is required.
- Per-user Apps Script quotas, concurrent execution limits and Drive capacity apply. No unlimited-free guarantee.
- PDF rendering uses pinned existing repo vendor assets through jsDelivr. Live verification of iframe CSP, cross-origin worker loading, mobile in-app browsers and multi-account Google behavior is still required. For production bundle/audit assets rather than relying on a third-party CDN.
- Drive/Sheets writes are not transactional across services. Detected write failures trash orphan files, but timeout reconciliation/recovery needs live testing.
- No live abuse controls, automated retention, analytics, migration, contact/event editor, Gmail integration or production sign-off yet.
- The manifest uses broad Drive access for this private owner-installed pilot. This is not the scope/verification design for distributing a public multi-user OAuth application.
- Do not delete or switch the existing Supabase deployment until migration and end-to-end checks succeed.

If the Google Workspace domain disallows anonymous web apps, the account administrator must permit it or the anonymous endpoint needs another host.
